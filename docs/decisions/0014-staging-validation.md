# ADR-0014 — Staging Deployment & Production Validation (M11 Phase 3)

- **Status:** Accepted
- **Date:** 2026-08-15
- **Owner:** @atoz/platform, @atoz/lead
- **Documents affected:** 08-deployment-strategy.md, 14-implementation-roadmap.md, docs/operations/002–007, CHANGELOG.md

## Context

Task 24 (M11 Phase 3) must prove production readiness through a
production-like staging environment without performing a real production
deployment or inventing external credentials. The staging layer must reuse
the frozen production security boundaries, remain a business-platform-only
surface, and produce automated evidence for every verification it can run.

## Decision

1. **Staging is an overlay, not a fork (Phase A).** `compose.staging.yml`
   is a thin compose override applied on top of `compose.prod.yml`
   (`docker compose -f compose.prod.yml -f compose.staging.yml`). It
   changes only identity (`name`, `APP_ENV`, domains, CORS); hardening,
   networks, resource limits, non-root read-only containers, and
   `${VAR:?}` secrets are inherited from production.

2. **Deployment is immutable and fail-closed (Phase B).** Images are built
   from the commit SHA and pushed to GHCR; a transient generated override
   (`compose.images.yml`, gitignored) pins every first-party service to
   the immutable tag. The pipeline runs pre-deploy validation, the
   all-stream migration gate, rollout, container readiness, the live smoke
   suite, and rolls back to the previous stored tag on failure. Production
   requires a manual dispatch plus the GitHub environment approval rule —
   never auto-deploy.

3. **Database validation is consolidated (Phase C).**
   `tools/db/validate-migrations.sh` verifies single heads, distinct
   version tables, fresh upgrade, schema smoke, tenancy columns, unique
   idempotency constraints, and downgrade/re-upgrade for all seven service
   streams. A new CI `staging` job runs it against fresh PostgreSQL.

4. **Smoke and failure suites are layered (Phases D/E).** The 24-item
   smoke matrix and the 12 failure scenarios are unit-tested in
   `tests/staging/` (mocks/fixtures, CI-every-push); the live counterparts
   are `tools/deploy/staging-smoke.sh` and `tools/deploy/rollback-test.sh`
   for host execution. Recovery is always asserted as failure -> detection
   -> retry/fallback -> recovery -> idempotency -> terminal state.

5. **Load and observability are threshold-driven (Phases F/G).**
   `tools/loadtest/baselines.yml` freezes p50/p95/p99, error-rate, queue
   depth, worker-time and DB-pressure targets; `locustfile.py` covers every
   scenario. `tools/observability/check-observability.sh` plus pytest
   verify Prometheus targets, SLO alerts, metrics, Grafana/Loki/OTel
   wiring, request-ID correlation, and credential-free logs.

6. **Backup/restore and rollback are drills (Phases H/I).**
   `tools/db/staging-recovery-drill.sh` seeds, backs up, destroys,
   restores, verifies rows + constraints + migrations + readiness, and
   records RPO/RTO evidence. `tools/deploy/rollback-test.sh` exercises
   deploy N -> N+1 -> controlled failure -> rollback N with DB
   compatibility and idempotency checks. DB rollback is never automatic:
   migrations are additive/forward-compatible by policy; destructive
   migration rollback requires a release window.

7. **External gates are reported, not faked (Phases K/L).**
   `docs/operations/007-staging-validation.md` is the blocker report:
   completed/automated evidence, failed/skipped checks, required
   credentials/infra/DNS/Vault/approvals, exact commands, and Go/No-Go
   prerequisites. Nothing that requires real infrastructure is marked
   complete.

## Consequences

- Staging and production share one hardened compose base; environment
  drift is limited to the overlay + env file.
- Deploying now requires a self-hosted `deploy` runner and repository
  secrets; until provisioned, the workflow fails fast (manual dispatch
  only).
- CI gains a `staging` job (fresh PostgreSQL migration validation) and
  the security job runs npm audit + the security guard; the quality job
  runs the staging and observability guards.
- The generated `compose.images.yml` is gitignored and contains no
  credentials; it is always regenerated by the pipeline.

## Contract compliance

- Business-layer only: no AI, no LLM SDKs, no prompts/embeddings/vector
  DB anywhere in the staging tooling; AI OS contact remains exclusively
  through `services/aios-bridge`.
- Tenancy and idempotency are verified at the database level (niche_id
  columns, unique constraints) and in the smoke/failure suites.
- All new tooling is verifiable in CI; live-only gates are reported as
  blockers with explicit owners and inputs.
